# rule-name

狀態：**草案，尚未實作／已實作**（擇一）。已實作時填入實際註冊的 lint 名稱；草案明確說明尚未提供診斷與 auto-fix，以下內容僅為規劃。

所有規則文件必須保留下列章節與順序，不得省略。規則特有的小節可放在對應章節內。沒有可列出的確定內容時，依情況填寫：

- 「無」：已確認沒有對應內容。
- 「待決策」：設計或政策尚未決定。
- 「未知」：資訊不足或尚未查核，無法確認。

同一章節可逐項標示待決策或未知的部分。

## 目的

描述希望統一的習慣與原因；區分本 repo 的風格政策與 Rust 的語意要求。

## 適用範圍

- 明確指定檢查對象，例如 imports、路徑使用點、derive 列表或型別定義，以及是否涵蓋所有可見性。
- 已實作規則引用[共用分析範圍](../architecture.md#分析範圍)，不重列來源發現、module 歸屬與獨立 `include!` 片段的共用條件；草案只能說明預定遵守的範圍。
- 涵蓋檔案頂層、inline module、函式、方法、closure、async block、控制流程與其他巢狀區塊中符合檢查對象的位置；不適用的位置另行列明。
- 涉及名稱、路徑或型別時，以 rustc 的實際解析結果為準，不靠名稱或檔案目錄猜測語意。
- 說明是否使用 compiler facts，以及是否檢查已載入檔案內 cfg 停用的程式碼。只補充原始巨集呼叫、derive 或其他與共用範圍不同的細節，未確認者列入未決事項。

## 規則

- 使用「必須」「禁止」「允許」描述可判定的條件，避免只寫偏好。
- 若涉及分組、排序或優先順序，列出確切順序、處理單位與未知項目的處理方式。
- 說明與其他規則的分工，不重複定義其他規則的政策。

## 正確範例

提供符合規則的 Rust 程式碼，交代必要的 module 結構、名稱來源或其他前提。

## 錯誤範例

提供對應的違規程式碼，說明違反哪項條件及預期改法。

## 政策例外

只列規則明確允許、不視為違規的情況；已確認沒有例外時填「無」，尚未定案時填「待決策」。

## 實作限制

只列本規則無法可靠分析、尚未支援或僅能診斷的情況，不重列架構文件的共用限制；尚未查核時填「未知」。

## Auto-fix

- 說明實際支援範圍，以及哪些情況僅診斷、不修正；草案必須寫明尚未提供，後續條件僅為規劃。
- 列出修正範圍、必須保留的語意與原文，以及註解、attributes、巨集或共用來源等相關安全邊界；共用的安全 attribute 清單與共用來源行為引用[架構](../architecture.md#安全邊界)，不在規則文件重列。
- 只補充本規則的 edits、縮排或換行處理差異，不重列架構文件的共用修正機制。

## 驗證與安全性依據

列出已驗證的 compiler／依賴版本、主要測試與對應版本的官方文件或來源依據，不將個別測試外推為所有情況皆安全。尚未實作且確認沒有驗證紀錄或依據的草案填「無」；尚未確認時填「未知」。固定工具鏈與測試檔案的存在，不等同於已執行驗證。

## 未決事項或後續規劃

只保留尚待決策或未支援的事項，不保留已完成的開發 checklist；尚未定案的事項標示「待決策」，已確認沒有待辦時填「無」。

完成實作後，以實際程式碼更新狀態、lint 名稱與支援邊界，並同步[規則索引](README.md)。移除不適用的模板提示，但保留完整章節與順序，缺少確定內容時依上述狀態填寫。
