# rule-name

## 目的

描述希望統一的習慣與原因；區分本 repo 的風格政策與 Rust 的語意要求。

## 適用範圍

- 明確指定檢查對象，例如 imports、路徑使用點、derive 列表或型別定義，以及是否涵蓋所有可見性。
- 檢查 Cargo／rustc 在當次 target、features 與 cfg 下實際載入的自有 Rust 來源。
- 涵蓋檔案頂層、inline module、函式、方法、closure、async block、控制流程與其他巢狀區塊中符合檢查對象的位置；不適用的位置另行列明。
- 涉及名稱、路徑或型別時，以 rustc 的實際解析結果為準，不靠名稱或檔案目錄猜測語意。
- 說明是否檢查 cfg 停用的程式碼；明確列出 rustdoc、巨集輸入、展開產物與 `include!` 實體來源的支援邊界，未確認者標為待確認。

## 規則

- 使用「必須」「禁止」「允許」描述可判定的條件，避免只寫偏好。
- 若涉及分組、排序或優先順序，列出確切順序、處理單位與未知項目的處理方式。
- 說明與其他規則的分工，不重複定義其他規則的政策。

## 正確範例

提供符合規則的 Rust 程式碼，交代必要的 module 結構、名稱來源或其他前提。

## 錯誤範例

提供對應的違規程式碼，說明違反哪項條件及預期改法。

## 例外

分開列出政策上允許的例外與實作上無法可靠判斷的限制；沒有就寫「無」，未決事項明確標為待確認。

## Auto-fix

- 說明是否支援，以及哪些情況僅診斷、不修正；不預設所有違規都能修正。
- 列出修正範圍、必須保留的語意與原文，以及註解、attributes、巨集或共用來源等相關安全邊界；共用的安全 attribute 清單與共用來源行為引用[架構](../architecture.md#安全邊界)，不在規則文件重列。
- 修正只需語法正確、語意不變，排版交給 rustfmt。
- 安全且可直接套用的修正使用 `MachineApplicable` suggestion，由 `cargo dylint --fix` 套用；規則不自行寫檔或呼叫 rustfmt。
- 需要查核的行為附上對應版本的官方文件或來源依據，不將個別測試外推為所有情況皆安全。
